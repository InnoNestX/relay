# 测试用例设计（生成逻辑）

## 适用角色
测试助手（主责）；临时测试助手可写稿，交测试助手合并。

## 触发条件
- 需求提测或即将提测，需要新写用例。
- 需求最终结论已定，需要按最终口径统一修改用例。
- 用户手动关闭某缺陷（口径变化），需要更新对应用例预期。

> **不触发**：需求还在讨论、变更未定稿 → 不改用例，只在口径台账记「讨论中」，提测时统一改。

## 输入
1. 需求正文、需求文档最新版、原型、接口文档。
2. 关联任务与关联缺陷（含已关闭的，用来补回归点）。
3. 需求讨论群里产品/研发发布的变更（由通知助手只读查）。
4. 口径台账（已有口径、已确认非 bug、本期不测）。
5. 权限分配文档 {PERMISSION_DOC}（涉及多角色时）。

## 分步流程

### 第 1 步：读需求，建「需求要点表」
逐段拆出可测试的要点，每条一行：
`要点编号 · 来源（文档章节/原型页/群消息）· 规则原文 · 涉及端 · 涉及角色`
同时标出：
- **差异**：需求与原型冲突、文档前后矛盾、文档与群里变更不一致；
- **缺口**：没写清的（默认值、上限、超时、排序、空状态、文案、错误提示、时区、取整规则）。

### 第 2 步：列差异，问口径
- 把差异和缺口整理成编号清单，**先查口径台账和群消息**是否已有答案。
- 没有答案的交主管 → 经通知助手问产品/研发（委婉格式）。
- 得到口径后写进口径台账：**日期、版本、谁说的、原文位置、影响用例**。
- 没得到口径前，用例标「待确认」，不阻塞其他用例的编写。

### 第 3 步：按维度拆用例（覆盖矩阵）
对每个要点，逐一过以下维度，适用就出用例：

| 维度 | 要覆盖的点 | 示例写法 |
|---|---|---|
| 正常流程 | 主路径、每个可选分支、每个入口 | 「从列表页进入 → 提交 → 详情页状态正确」 |
| 异常 | 必填缺失、格式错误、依赖服务失败、网络中断、超时、第三方回调失败 | 「第三方返回失败时，单据回滚并给出可理解提示，不直接显示错误码」 |
| 边界 | 最小/最大值、刚好等于、±1、空、超长、特殊字符、临界时间点（如 14:59:59 / 15:00:00 / 15:00:01） | 「数量等于上限可提交；上限+1 被拦且提示上限值」 |
| 状态流转 | 每个合法流转、每个非法流转、终态不可逆、并行状态冲突 | 「已取消的单据不能再被确认」 |
| 幂等 | 重复提交、重复回调、重试、刷新后重复操作 | 「同一回调重复 3 次，只处理一次，余额变动只发生一次」 |
| 并发 | 多端同时操作、多账号抢同一资源、多 IP 同时提交 | 「两个账号同时占用最后 1 个名额，只有 1 个成功」 |
| 乱序/延迟 | 回调先到后到、延迟到达、过期后到达 | 「失败回调晚于成功回调到达，最终状态仍为成功」 |
| 权限与数据范围 | 每个角色能见的菜单、能操作的按钮、能看到的数据范围、越权访问 | 「子组织操作员只能看到被授权组织的数据，改 URL 参数访问其他组织返回无权限」 |
| 展示与格式 | 金额/数量小数位、时区、多语言、空状态、长文本截断、乱码 | 「展示类金额统一两位小数；输入框保持整数」 |
| 兼容与环境 | 端（移动网页/PC/App）、视口、浏览器、弱网 | 「移动视口 430×932 下按钮不遮挡」 |
| 数据一致性 | 前台与后台、列表与详情、报表与明细、导出与页面 | 「报表汇总值 = 明细之和」 |
| 跑批/定时 | 定时任务触发前后、T+1 数据 | 「跑批前不显示，跑批后显示；跑批前看不到不算缺陷」 |
| 回归 | 关联缺陷（含已关闭）复现点、被改动影响的老功能 | 「#历史缺陷 场景不再复现」 |

拆分原则：
- **一条用例只验证一个预期**；多个预期拆多条。
- 前置**增量书写**：公共前置只在文档开头写一次，单条只写额外前置。
- 异常用例的预期必须写清「**合理兜底 + 易用性提示**」，不能接受「直接甩错误码」。
- 本期不测的写进「本期不测」并标灰，不出用例或出用例标「本期不测」。

### 第 4 步：定优先级与类型
- 优先级：P0 / P1 / P2（判定细则未统一，见 GAPS；默认：主路径与金额与数据正确性类 P0，常用异常与权限 P1，展示与低频边界 P2）。
- 类型：功能 / 异常 / 边界 / 权限 / 性能 / 兼容 / 回归。
- 编号：`TC-<端>-<模块>-<F|E>-NNN`（F=功能，E=异常/边界），如 `TC-WEB-ORDER-F-001`、`TC-ADM-REPORT-E-016`。

### 第 5 步：产出三份同源文件
放在 `<工作目录>/<需求简称>/`：
1. `<需求ID>_cases.md`——给人看；
2. `<需求ID>_cases.json`——给缺陷助手批量落库（结构见 `templates/test-cases.schema.json`）；
3. `<需求ID>_cases.<富文本>.html`——可视化稿，浏览器直接打开，同时作为落库格式（{DEFECT_SYSTEM_RICH_FORMAT}）。

三份必须**同源生成**（从 json 渲染出 md 与 html），条数一致。

### 第 6 步：自评审后提交评审
按 `test-case-review` 的自查清单过一遍，再交评审。

## 文档结构（md 与 html 一致）
```text
# <需求ID>-<需求简称> 测试用例
## 摘要表
| 需求文档 | 需求条目 | 原型 | 用例文档自身 | 环境 |   ← 全部可点链接
## 公共前置（只写一次）
## 待确认清单（编号，含差异来源与当前默认）
## 覆盖一览（要点 × 维度矩阵；各优先级条数）
## 模块 A
### TC-WEB-A-F-001 标题
- 优先级 / 类型 / 模块
- 前置（增量）
- 数据
- 步骤 1. 2. 3.
- 预期
## 模块 B …
## 本期不测
## 变更记录（MM-DD 按 <口径/缺陷单> 更新了哪些条）
```

## 判定规则
- 需求与原型冲突 → 列差异问，不自行选一个。
- 群里变更新于文档 → 以群里为准，但只采纳**已定稿**的；讨论中的标待确认。
- 用户手动关单 → 对应用例预期按关单口径更新，并注「MM-DD 按 #单号 关单口径更新」。

## 交接对象
- 评审：见 `test-case-review`。
- 落库：缺陷助手（`test-case-publish`）。
- 口径问题：主管 → 通知助手。

## 禁止项
- 自己写缺陷系统（落库交缺陷助手）。
- 需求未定稿就改用例。
- 预期写「系统报错」「提示错误码」这种不可判定的描述。
- 一条用例塞多个预期。

## 常见错误
- 只写正常流程，漏了幂等、并发、乱序。
- 前置每条都抄一遍，文档冗长。
- md 和 json 条数不一致（手工分别改导致）。
- 没把关联的已关闭缺陷转成回归用例。

## 自检清单
- [ ] 每个要点至少过了一遍覆盖矩阵
- [ ] 差异/缺口已编号列出，已得到口径的写进台账
- [ ] 异常预期有兜底与友好提示
- [ ] 三份文件同源、条数一致、链接可点
- [ ] 优先级与类型每条都有
- [ ] 本期不测已单列
